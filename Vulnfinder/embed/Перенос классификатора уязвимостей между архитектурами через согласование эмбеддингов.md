## 0. Краткая концепция 

Существуют модели классификации уязвимостей по бинарному, ассемблерному или декомпилированному коду, обученные преимущественно на x86/x86-64. Для менее представленных архитектур - ARM/AArch64, MIPS и др. - размеченные данные могут быть ограничены. Предполагается, что можно получить парный корпус программных функций, скомпилировать каждую функцию для двух ISA, извлечь эмбеддинги обеих бинарных реализаций и обучить преобразование, совмещающее представления целевой архитектуры с пространством исходного x86-классификатора.

> [!idea]
> **Основная идея:** обучить отображение **без использования меток уязвимости целевой архитектуры**, а затем пропускать преобразованные ARM-эмбеддинги через **замороженную голову классификатора** x86. Исследование должно проверить, сохраняются ли при таком переносе не только геометрические расстояния между эмбеддингами, но и решения модели на границе *safe/vulnerable*.

**Потенциальный вклад:** систематическое сравнение post-hoc constant shift, линейного и нелинейного alignment для *frozen* детектора; выявление связи между ошибкой геометрического alignment и потерей качества vulnerability classification; при необходимости - обучение decision-preserving alignment с ограничением на различие классификационных оценок.

### Вопрос исследования

> [!goal]
> **«Перенос классификаторов уязвимостей бинарного кода между архитектурами процессоров посредством согласования эмбеддингов без меток уязвимостей целевой архитектуры».**
> 
## 1. Математическая формализация

### 1.1. Объекты и обозначения

> [!def]
> Условно
> - $f$ — функция на C/C++ из исходного проекта
> - $C_x(f;\theta_x)$ — компиляция в x86-64 при настройках $\theta_x$ (компилятор, флаги, ABI и т. д.)
> - $C_a(f;\theta_a)$ — компиляция той же функции в AArch64
> - $E_x$ и $E_a$ — экстракт векторов из бинарных представлений соответствующих ISA
> - $z_x=E_x(C_x(f;\theta_x))\in\mathbb R^{d_x}$
> - $z_a=E_a(C_a(f;\theta_a))\in\mathbb R^{d_a}$
> - $h_x:\mathbb R^{d_x}\to[0,1]$ — замороженный классификатор уязвимостей, обученный на x86-64
> - $T_{a\to x}:\mathbb R^{d_a}\to\mathbb R^{d_x}$ — обучаемый архитектурный адаптер
> - $y_x,y_a\in\{0,1\}$ — истинные метки уязвимости бинарных реализаций
> 

Классификация на ARM через преобразование:

$$
{\hat y_a=\mathbb{1}\!\left[h_x(T_{a\to x}(z_a))\ge\tau\right]}
$$

где $\tau$ — порог, выбранный **без просмотра тестовых ARM-меток**.

### 1.2. Первоначальная гипотеза о постоянном дрейфе

Предполагается существование общего вектора смещения:

$$
{z_x\approx z_a+\Delta_{a\to x}}.
$$

При одинаковой размерности эмбеддингов ($d_x=d_a$), по парному корпусу $\mathcal D_p=\{(z_x^{(i)},z_a^{(i)})\}_{i=1}^N$ оптимальный постоянный сдвиг относительно среднеквадратичной ошибки равен:

$$
\Delta^* = \arg\min_{\Delta}\sum_{i=1}^N\|z_x^{(i)}-z_a^{(i)}-\Delta\|_2^2
=\frac1N\sum_{i=1}^N\left(z_x^{(i)}-z_a^{(i)}\right).
$$

> [!theorem]
> **Нулевая baseline-гипотеза**: достаточно глобального смещения эмбеддингов, характерного для архитектуры.

> [!nb]
> **Слабое место:** архитектурные различия скорее зависят от самой функции. Если $z_x=Rz_a$, то $\Delta_i=(R-I)z_a^{(i)}$, и единого сдвига для всех $f_i$ нет. При разных размерностях исходную форму со сложением использовать нельзя без предварительного проектирования в общее пространство.

### 1.3. Более общая гипотеза

$$
{T_{a\to x}(E_a(C_a(f)))\approx E_x(C_x(f))}.
$$

> [!def]
> Надёжнее разделить **две** гипотезы:
> 
> - **H0 - representational alignment:** существует относительно простое $T$, уменьшающее ошибку между эмбеддингами парных функций на новых проектах.
> - **H1 - decision-preserving transfer:** применение $h_x\circ T$ сохраняет качество обнаружения уязвимостей ARM при контролируемом числе ложных тревог.

$\mathrm{H0}\not\Rightarrow\mathrm{H1}$: низкое среднее расстояние между эмбеддингами не гарантирует совпадения предсказаний у разделяющей поверхности классификатора.

## 3. Дизайн экспериментов

> [!list]
> 0. Проверка жизнеспособности исходного классификатора
> 1. Получить воспроизводимый бинарный классификатор $E_x+h_x$, работающий на **независимых** x86-64 функциях.
> 2. Проверить binary positive recall, precision, FPR, PR-AUC, calibration.
> 3. Проверить устойчивость к `-O0`/`-O2` и stripped/symbol normalization.
> 4. Заморозить checkpoint и выбрать источник классификационной головы.

1. Есть ли постоянный cross-architecture drift?

- Измерить $\Delta_i=z_x^{(i)}-z_a^{(i)}$, среднее и ковариацию.
- Проверить распределение $\|\Delta_i-\bar\Delta\|$ на новых проектах.
- Разделить по size/CFG complexity/compiler/optimization.
- Сравнить MSE, cosine similarity и *retrieval recall@k* для парных функций.

**Ожидаемый диагностический результат:** если дисперсия $\Delta_i$ велика, один общий вектор недостаточен.

2. Linear vs nonlinear mapping

Тренировать shift, Procrustes, ridge/affine, MLP; удерживать параметры адаптеров минимальными. Использовать одинаковые пары train/validation и одинаковый frozen source classifier. Строить **learning curves** от 1k/5k/20k/100k обучающих пар (ориентировочные точки, при доступности корпуса).

3. Cross-ISA vulnerability transfer

На held-out vulnerable/fixed функциях сравнить:

| Конфигурация                                   | Назначение                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| x86 → x86 classifier                           | Source ceiling, при известных условиях                                                |
| ARM encoder → frozen x86 head без $T$          | Direct transfer lower baseline; только если пространства совместимы                   |
| ARM → constant shift → x86 head                | Проверка первоначальной идеи                                                          |
| ARM → Orthogonal Procrustes → x86 head         | Геометрическое базовое преобразование                                                 |
| ARM → ridge/affine → x86 head                  | Линейная адаптация                                                                    |
| ARM → MLP adapter → x86 head                   | Нелинейная адаптация                                                                  |
| ARM → geometry + prediction consistency → head | Decision-preserving objective                                                         |
| Architecture-normalized IR/P-code baseline     | Альтернатива адаптеру в embedding space                                               |
| Target-supervised ARM classifier               | Оценка потолка при доступности ARM labels; **нечестно сравнивать по annotation cost** |
