# как работать с zeroSuite

Это практическая инструкция по исследовательскому харнессу zeroSuite: установка, запуск, режимы, последовательность исследования и готовые промпты. Она предназначена для работы в Linux или WSL2 со своими прошивками и бинарниками.

Главное: zeroSuite — не кнопка «найти RCE», а харнесс для доказательного исследования. Он помогает построить модель программы, собрать свидетельства, проверить гипотезы, воспроизвести их в изолированной лаборатории и только затем оценить exploitability.

## 1. Что харнесс делает

Основной рабочий контур:

```text
Case + scope
    ↓
Intake → Program model → Threat model
    ↓
Ghidra/REA + Evidence + Semantic Search + Dependency analysis
    ↓
Prior-research → Hypothesis store → Static investigation/review
    ↓
Runtime reconstruction → Directed experiments / fuzzing
    ↓
Minimal PoC + claim-specific oracle
    ↓
Primitive proof → Exploit KB → Bounded exploit experiment
    ↓
Independent replay / reliability / reports / ledger
```

Это не обязательная линейная последовательность. Можно параллельно проверять несколько гипотез, возвращаться к статике после динамики и оставлять часть вопросов в `UNKNOWN`.

Важные свойства:

- исходный бинарник и каталог prior-research являются read-only входами;
- каждый вывод привязывается к SHA-256 бинарника, analysis profile, address space и версии инструментов;
- старые отчёты, Semantic Search и dependency analysis производят **leads**, а не готовые уязвимости;
- target, PoC, fuzz engine, harness, debugger и emulator запускаются **только в Docker**;
- bug verdict, динамическое наблюдение, exploitation primitive и итоговый exploit — разные уровни доказательности;
- секреты нельзя помещать в промпты, `AGENTS.md`, отчёты, case или экспортируемые артефакты.

Основной сценарий — нативные ELF и PE для x86, x86-64, ARM32 и AArch64. Для native fuzzing по умолчанию используется AFL++ в Docker; libFuzzer, honggfuzz и Jazzer — вторичные engine, выбираемые явно. Поддержка конкретного файла всё равно зависит от его ABI, runtime и возможности построить корректный harness/profile.

## 2. Что подготовить

Рекомендуемая среда — linux у исследователя. Нужны:

- Docker Engine с Docker Compose; Docker daemon должен быть доступен из WSL;
- Ghidra и Java 21+;
- Node.js, совместимый с vendored REA; для текущего REA требуется Node.js 24.22.1 или новее;
- `sqlite3` с поддержкой `-json`, `readelf`, `objdump`, `python3`;
- для локального Semantic Search с embedding/indexing — NVIDIA GPU и NVIDIA container runtime.

Полезные, но необязательные утилиты: `rg`, `file`, `strings`, `xxd`, `jq`, `curl`, `unzip`, `tar`, `sha256sum`, `dtc`. В Debian/Ubuntu пакет для `dtc` называется `device-tree-compiler`.

Подготовьте три отдельных места:

```text
/absolute/path/to/zeroSuite/          сам харнесс, его не используем как research workspace
/absolute/path/to/research-workspace/ распакованная прошивка и связанные файлы
/absolute/path/to/results-.../        результаты первичного анализа, если они есть
```

В research workspace удобно держать всю прошивку, а не только один бинарник: конфигурацию, скрипты запуска, библиотеки, соседние сервисы и документацию. Основной target задаётся отдельно через `ZEROSUITE_ELF`.

`ZEROSUITE_RESULTS` — это каталог результатов предыдущего/первичного анализа, в терминах харнесса **prior-research**. Поддерживаемые результаты импортируются как исторические кандидаты. Старые `CONFIRMED`, адреса и exploit chains автоматически не переносятся в текущее исследование.

## 3. Настройка окружения

Ниже рекомендуемый полный запуск с Kimi и prior-research. Пути и имя target замените на свои. Выполняйте команды в одном shell от обычного пользователя.

```bash
cd /absolute/path/to/research-workspace

export ZEROSUITE_ELF="$PWD/usr/sbin/httpd"
export ZEROSUITE_RESULTS="/absolute/path/to/results-httpd"
export ZEROSUITE_TOOL_VERSION="11.2"
export ZEROSUITE_TOOL_GHIDRA="/absolute/path/to/ghidra_11.2_PUBLIC"

# Явный Kimi preset. Model/token env/base URL у него уже есть по умолчанию.
export ZEROSUITE_PROVIDER="kimi"
read -rsp "KIMI_API_KEY: " KIMI_API_KEY; export KIMI_API_KEY; echo

source /absolute/path/to/zeroSuite/env.sh

# Значение по умолчанию для workspace вне каталога установки; указано явно для ясности.
export ZEROSUITE_CASE_ROOT="$ZEROSUITE_WORKSPACE/.zerosuite-case"

# Необязательно: разрешить новому case ограниченную сборку и запуск agent-created Docker lab.
export ZEROSUITE_RUNTIME_LAB=1
```

Не вставляйте реальный API key в файл, команду с сохранением в историю shell или сообщение агенту. `read -rsp` вводит его без отображения. Токен нужен только в operator environment.

Назначение переменных:

| Переменная | Назначение |
|---|---|
| `ZEROSUITE_ELF` | Абсолютный путь к основному исследуемому файлу. Обязателен для нового case. Несмотря на имя, переменная используется и для поддерживаемых PE. |
| `ZEROSUITE_RESULTS` | Абсолютный путь к prior-research. Для обычного `zerosuite` необязателен, но текущий `zerosuite.prepare` требует существующий каталог. |
| `ZEROSUITE_TOOL_GHIDRA` | Абсолютный путь к каталогу установки Ghidra. `env.sh` передаёт его REA как `GHIDRA_INSTALL_DIR`. |
| `ZEROSUITE_TOOL_VERSION` | Версия Ghidra. При `zerosuite.prepare` должна точно совпадать с `application.version` в установленной Ghidra. |
| `ZEROSUITE_IMAGE_BASE` | Необязательный известный image base, например `0x400000`. Не угадывайте его: без значения неизвестное остаётся `null`, а привязка старых адресов может остаться `PARTIAL_BINDING`. |
| `ZEROSUITE_CASE_ROOT` | Каталог case. По умолчанию — `.zerosuite-case` внутри research workspace. |
| `ZEROSUITE_PROVIDER` | Необязательный явный provider. Для Kimi используйте `kimi`; иначе provider/model можно выбрать через `/models` в OpenCode. |
| `ZEROSUITE_MODEL` | Явная модель compatible endpoint. Для текущего Kimi preset по умолчанию — `k3.1-pro`. |
| `ZEROSUITE_TOKEN_ENV` | Имя переменной с токеном. Для Kimi preset — `KIMI_API_KEY`. |
| `ZEROSUITE_BASE_URL` | URL OpenAI-compatible endpoint. Для Kimi preset уже задан; для custom provider задайте явно. |
| `ZEROSUITE_RUNTIME_LAB` | При значении `1` добавляет новому case ограниченные полномочия `lab.build`/`lab.run`. Существующий scope эта переменная задним числом не меняет. |

Если prior-research нет, можно не задавать `ZEROSUITE_RESULTS` и запустить `zerosuite` напрямую после настройки target/provider. Текущий `zerosuite.prepare` рассчитан на полный сценарий и проверяет `ZEROSUITE_RESULTS` обязательно.

Если не нужен явный Kimi preset, не задавайте provider variables: после запуска выберите модель штатной командой `/models` и авторизуйте provider средствами OpenCode.

## 4. Semantic Search и tmpfs

Semantic Search нужен для поиска семантически похожих функций и получения дополнительных leads. Он не заменяет Ghidra/REA и не подтверждает reachability или уязвимость.

Для **новой локальной индексации через host-analysis worker** нужен отдельный ограниченный tmpfs. Пример для нового, не занятого пути:

```bash
sudo install -d -m 0700 -o "$(id -u)" -g "$(id -g)" /srv/semsearch-analysis-work
sudo mount -t tmpfs \
  -o "size=2G,nosuid,nodev,noexec,mode=0700,uid=$(id -u),gid=$(id -g)" \
  tmpfs /srv/semsearch-analysis-work
```

Это временный mount до перезагрузки. Не выполняйте эти команды поверх уже существующего или содержащего данные пути, предварительно не проверив его назначение.

tmpfs не нужен для каждого статического исследования. На хосте без NVIDIA GPU можно обращаться к уже работающему совместимому Semantic Search endpoint, но локальный lifecycle `open` и локальные embedding/indexing требуют GPU. Если bundled Semantic Search ещё не запущен, обычный `zerosuite.prepare` попытается поднять его и проверит NVIDIA runtime.

## 5. Подготовка и запуск

В том же shell, где заданы переменные:

```bash
zerosuite.prepare
zerosuite
```

`zerosuite.prepare`:

- проверяет target, prior-research, Ghidra, Java, REA, Docker и host utilities;
- проверяет соответствие SHA-256 target и привязку prior-research;
- собирает отсутствующие lab/AFL++/Jazzer Docker images;
- при необходимости создаёт приватную конфигурацию Semantic Search;
- поднимает или проверяет сервисы и готовит case;
- запускает диагностику REA MCP и Ghidra provider.

Первая подготовка может быть долгой: скачиваются pinned images и модель, выполняется Ghidra/REA doctor, импортируется prior-research. Не запускайте `sudo zerosuite.prepare`: так теряется exported environment, а case files могут оказаться созданы от root. Скрипт сам при необходимости использует `sudo` для Docker/AppArmor.

После успешной подготовки повторная проверка без изменения установки:

```bash
zerosuite.prepare --check
```

Затем `zerosuite` показывает баннер `ZER0SUITE` и открывает OpenCode TUI. Большой prior-research может импортироваться до появления окна; стадии `inventory`, `table:*`, `directory:*`, `program-evidence`, `prior-bind` означают работу, а не зависание. Импорт resumable: после прерывания следующий запуск продолжает с checkpoint.

Повторный запуск в том же workspace с тем же case/provider/model возобновляет сессию. Другой workspace получает независимый `.zerosuite-case`.

## 6. Режимы работы

Переключение primary agents в TUI выполняется через **Shift+Tab**.

| Режим | Возможности | Когда использовать |
|---|---|---|
| `research` | Доменные zeroSuite/REA tools, ограниченные typed workspace writes; общие host shell/edit запрещены. Исходные workspace files защищены, кроме явно разрешённых путей. | Когда нужен максимально ограниченный scope-only контур. |
| `research-auto` | Все возможности `research` плюс built-in read/write/execute внутри workspace. Доступ за пределы workspace требует отдельного подтверждения. | **Рекомендуемый основной режим** для полного исследования, создания отчётов, скриптов и лабораторий. |

`research-auto` не снимает главное ограничение: даже с shell нельзя запускать target, PoC, fuzzer, debugger или emulator на host. Для этого используются typed Docker tools.

Отдельный `/init` agent — не третий исследовательский режим. Он изучает workspace и может изменять **только `AGENTS.md`**. Последующие `research/` отчёты, модель программы и лаборатории создаются уже основным агентом.

## 7. Как давать задачи агенту

Не пытайтесь уложить всё исследование в один промпт. Работайте этапами, проверяйте результат и давайте следующий ограниченный шаг.

Хороший запрос содержит:

1. объект и цель;
2. разрешённые источники и инструменты;
3. ожидаемый артефакт;
4. ограничения и критерий остановки.

Пример плохого запроса: «Проверь всех и проставь всем CONFIRMED/REFUTED». Он провоцирует необоснованные вердикты. Правильно требовать `CONFIRMED`, `REFUTED` **или `UNKNOWN` с конкретным blocker и следующим экспериментом**.

Полезные продолжения:

```text
Продолжи текущий этап по сохранённому task state. Не начинай анализ заново и не повторяй уже собранные evidence. Сначала проверь статус активных jobs, затем выполни один следующий недостающий шаг.
```

```text
Не повышай imported/semantic/dependency lead до текущего verdict без свежих address-bound evidence и skeptic review. Если доказательств недостаточно, оставь UNKNOWN и назови минимальный следующий эксперимент.
```

## 8. Рекомендуемый порядок и готовые промпты

Примеры ниже основаны на реальных диалогах с харнессом, но переписаны так, чтобы лучше соответствовать evidence gates. Подставьте тип устройства, target и цель своего проекта.

### Этап 1. Инициализация workspace

```text
/init Это workspace распакованной прошивки роутера. Основной target — usr/sbin/httpd; остальные binaries, libraries, configs и startup scripts относятся к той же прошивке. Цель исследования — найти и воспроизводимо проверить реалистичные pre-auth уязвимости, в первую очередь пути к RCE с минимальными предусловиями. В ZEROSUITE_RESULTS импортирован prior-research именно для текущего target. Изучи структуру проекта, существующий AGENTS.md и доступные метаданные. Зафиксируй в AGENTS.md только проверенные сведения: назначение проекта, основной target, важные пути, особенности запуска, ограничения prior-research и правила безопасной работы. Не переноси исторические verdicts как текущие и не выдумывай архитектуру или команды.
```

`/init` создаёт/обновляет только `AGENTS.md`. Если нужна поправка, не повторяйте полный анализ:

```text
/init Прочитай текущий AGENTS.md и сделай focused correction по уже собранным фактам. Не повторяй полный разбор прошивки и не открывай заново большие prior-research exports. Исправь только неточные identity, пути и ограничения; перечитай результат и устрани противоречия.
```

### Этап 2. Program model и threat model

```text
На основе текущего workspace и AGENTS.md построй модель программы для основного target и модель угроз устройства. Восстанови service → binary → config → interfaces, назначение, привилегии, протоколы, состояния аутентификации, входы, trust boundaries, assets и abuse cases. Отделяй наблюдения из configs/binary от предположений: socket не доказывает прикладной протокол, а строка не доказывает attacker-controlled input. Сохрани результаты в research/01-program-model.md и research/02-threat-model.md. Для каждого приоритетного направления укажи конкретный вход, security boundary, потенциальный эффект и unresolved conditions. Не проверяй пока отдельные уязвимости и не выдавай abuse cases за CONFIRMED.
```

### Этап 3. Восстановление runtime и лаборатории

```text
Создай минимально достаточную Docker-лабораторию для текущего hash-bound target. Сначала используй workspace_lab_scaffold, чтобы заново определить architecture, ABI, imported NVRAM symbols и target identity. Затем собери image и пройди validate → minimal → smoke → loopback; debug используй только для конкретного неразрешённого вопроса. Зафиксируй loader/sysroot/kernel/device gaps, oracle, reset behavior, resolved image ID и evidence_path каждого запуска. Не запускай target на host и не выдавай эмуляцию за поведение физического устройства.
```

Если есть лаборатория от другой версии прошивки:

```text
Изучи старую runtime-lab только как методический reference. Не копируй из неё target hashes, адреса, ABI assumptions, NVRAM values или verdicts. Сгенерируй новую lab для текущего target через workspace_lab_scaffold, перенеси только применимые механизмы и доведи её до validate/minimal/smoke. Все отличия и потери fidelity зафиксируй.
```

Если для lab нужен другой бинарник из этой же прошивки, агент должен сначала использовать `scope_extend`. Он покажет путь, SHA-256, операции и бюджеты; только после подтверждения оператора новый target попадёт в отдельный scope. Не просите агента обойти это подтверждение.

### Этап 4. Evidence, Ghidra/REA, Semantic Search и зависимости

```text
Проанализируй зависимости основного target и связанных сервисов. Используй свежие REA/Ghidra observations для imports, versions, code presence и reachability; Semantic Search применяй как дополнительный источник function leads только для exact artifact identity. Сопоставь подтверждённые package versions с известными advisories/1-day. Отдельно оцени VERSION_UNKNOWN, backports, наличие уязвимого кода, конфигурацию и reachability. Version/advisory match считай POTENTIALLY_AFFECTED, а не уязвимостью. Сохрани матрицу dependency → version evidence → advisory → code presence → configuration → reachability → next evidence в research/03-dependencies.md.
```

Холодный Ghidra import может занимать минуты. Не требуйте повторно открывать target после каждого timeout. Если агент говорит, что tool отсутствует, попросите его сначала выполнить Code Mode `search(...)` по конкретным возможностям, а не судить по сокращённому inline catalog.

### Этап 5. Отбор prior-research кандидатов

```text
Проанализируй imported prior-research и отбери 5 лучших кандидатов с потенциалом на pre-auth RCE либо RCE с минимальными базовыми предусловиями. Дедуплицируй report projections и не считай несколько представлений одной находки независимыми доказательствами. Ранжируй по attacker-controlled input, reachability, привилегиям, эффекту, стоимости проверки и blockers. Сделай только краткую свежую sanity-проверку, без PoC, эксплоитов и fuzzing. Для каждого кандидата выведи canonical ID, источник, historical address, bug class, предусловия, причину приоритета и минимальное next evidence. Исторические verdicts не переноси; при PARTIAL_BINDING адреса считай только leads.
```

Можно заменить 5 на 10, но небольшая первая выборка обычно удобнее для глубокой проверки.

### Этап 6. Статическая проверка кандидатов

Работайте с одним или небольшим числом кандидатов за запрос:

```text
Проведи static investigation/review кандидата [ID или historical address]. Сформулируй один проверяемый invariant и цепочку input → source → reachable path → guards/checks → sink → security effect. Получи свежие address-bound evidence из текущего бинарника через REA/Ghidra; при спорных инструкциях сверься с objdump. Проверь размеры, знаки, lifetime, cleanup, защитные ветви и unresolved indirect calls. Обязательно собери опровергающие аргументы и проведи skeptic review. Итог — CONFIRMED, REFUTED или UNKNOWN. CONFIRMED требуй только при полной цепочке; REFUTED — при конкретной защите или недостижимости; для UNKNOWN назови один blocker и самый дешёвый следующий эксперимент.
```

Полезный следующий запрос:

```text
Продолжи работу с оставшимися приоритетными кандидатами по той же методике. Не требуй от каждого обязательного CONFIRMED/REFUTED и не считай отсутствие crash опровержением. Сохрани rejected chains, conflicts и ограничения coverage.
```

### Этап 7. Directed experiments и fuzzing

Сначала направленный эксперимент:

```text
Для гипотезы [ID] сформулируй один динамический вопрос, claim-specific oracle, positive input, negative control, reset policy и ожидаемый observable path. Выбери минимальный существующий runtime profile или доработай текущую Docker lab. Выполни направленные эксперименты только в контейнере, сохрани run IDs/evidence paths и отдельно опиши, что именно наблюдалось. Crash без claim-specific oracle не подтверждает гипотезу, а отсутствие crash её не опровергает.
```

Затем, если есть воспроизводимый вход и reset:

```text
Подготовь и запусти ограниченную Docker fuzz campaign для [конкретный entrypoint/input interface]. Используй AFL++ по умолчанию и architecture-matched image; secondary engine выбирай только с явной причиной. Зафиксируй exact target/harness hash, seeds, dictionary, coverage, reset model, security oracle, run/wall/crash budgets и checkpoints. Выполни preflight, запусти campaign через доступный typed workflow и проверяй durable status вместо повторного запуска того же job. Findings считай unverified leads: выполни triage, negative control, минимизацию и три clean replay. Не повышай crash до CONFIRMED или exploitation primitive автоматически.
```

Фоновые fuzz jobs продолжаются независимо от текущего ответа агента. Можно параллельно исследовать другого кандидата, затем запросить:

```text
Проверь статус активных fuzz jobs по сохранённым job IDs. Для завершённых jobs изучи checkpoints/findings и продолжи triage; для активных не создавай дубликат той же campaign.
```

### Этап 8. Минимальный PoC и primitive

```text
Для воспроизведённого finding [ID] построй минимальный PoC, сохраняющий claim-specific oracle. Сначала проверь negative control, затем минимизируй вход и выполни три clean container replay на том же approved target/profile/image. Отдельно оцени exploitation primitive: какие байты/адреса/размеры контролируются, каковы preconditions, mitigations, timing, observability и repeatability. Используй PRIMITIVE_DEMONSTRATED только при непосредственно наблюдаемом primitive. Если виден только crash или INFOLEAK, не повышай результат до arbitrary write или code execution.
```

### Этап 9. Exploit development и независимая проверка

Этот этап начинается только после текущего `CONFIRMED` claim и `PRIMITIVE_DEMONSTRATED`:

```text
Для подтверждённого primitive [ID] выбери weakest sufficient security objective и используй только применимые hash-pinned Exploit KB references. Предпочти наблюдаемый infoleak или application state change более сложной control-flow цепочке. Проверь scope, objective, mitigations, budgets, stop rules и negative control. Выполни bounded development replay, затем независимый clean replay и оценку reliability. Bug verdict и exploit outcome не смешивай. Если primitive не доказан или objective отсутствует в scope, остановись с явным blocker, а не обходи gate.
```

Успешный development run — ещё не надёжный эксплоит. Для `REPRODUCIBLE` нужен свежий replay; все ограничения profile/fidelity сохраняются в выводе.

### Этап 10. Итоговый отчёт

```text
Сформируй итоговый отчёт из case store и saved evidence, а не из впечатлений диалога. Раздели imported candidates, freshly reverified claims, REFUTED, UNKNOWN, dynamic observations, demonstrated primitives и exploit outcomes. Для каждого результата укажи target SHA-256, analysis identity, address space, tool/profile versions, evidence/run IDs, fidelity и ограничения воспроизведения. Для UNKNOWN перечисли blockers и следующие минимальные эксперименты. Проверь redaction: в отчёте не должно быть API keys, tokens или секретов прошивки.
```

## 9. Как читать вердикты

- **`CONFIRMED`** — установлены controlled input, достижимый путь, нарушенный invariant и security effect. Есть свежие evidence и skeptic review.
- **`REFUTED`** — найдена конкретная защита, contract или недостижимость, закрывающая именно эту гипотезу. «Не упало» сюда не относится.
- **`UNKNOWN`** — корректный результат с конкретным blocker и следующим ограниченным экспериментом.
- **`PARTIAL_BINDING`** — prior-research не имеет полной identity/address binding. Старые адреса нельзя автоматически считать текущими typed addresses.
- **Crash/fuzz finding** — наблюдение/lead до triage, negative control и clean replay.
- **`PRIMITIVE_DEMONSTRATED`** — отдельно наблюдаемый exploitation primitive, а не просто crash, CWE или decompiler pattern.

## 10. Где искать результаты

Внутри research workspace:

```text
.zerosuite-case/       case store, CAS, OpenCode home, checkpoints и служебные данные
research/              рекомендуемое место для ваших моделей, заметок, labs и отчётов
AGENTS.md              краткие проверенные инструкции для будущих сессий
```

Markdown reports и worklog являются проекциями store/events. Ручная правка проекции сама по себе не создаёт доказательство. Исходные target и prior-research не изменяйте.

## 11. Типовые проблемы

**`NEEDS_TARGET`** — не задан или недоступен `ZEROSUITE_ELF`.

**`TOKEN_REQUIRED`** — выбран explicit compatible provider, но отсутствует токен в указанной token environment variable.

**Ghidra version mismatch** — `ZEROSUITE_TOOL_VERSION` не совпадает с `Ghidra/application.properties` в каталоге `ZEROSUITE_TOOL_GHIDRA`.

**Semantic Search не поднимается без GPU** — для bundled local embedding нужен NVIDIA runtime. Используйте уже работающий совместимый endpoint либо выполняйте исследование без локального Semantic Search; не подменяйте его случайным vector index.

**Окно OpenCode долго не появляется** — вероятен большой prior-research import. Смотрите стадии в `stderr` и не удаляйте case: import возобновляемый.

**`BUDGET_EXCEEDED` для текущего target** — агент может пополнить bounded operations/budgets через `scope_authorize` в рамках уже авторизованного target. Это не разрешение расширяться на другие файлы.

**Нужен ещё один бинарник из прошивки** — требуется двухшаговый `scope_extend` с показом summary и подтверждением оператора.

**Агент сообщает, что tool недоступен** — попросите сначала использовать Code Mode `search(...)` по конкретной возможности и затем вызвать найденный exact tool path.

**Агент просит запустить target на host** — остановите это направление: target/PoC/fuzzer/debugger/emulator должны выполняться через typed Docker workflow.
